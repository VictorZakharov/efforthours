# Manual-QA work-item review rubric 1.0.0

## Status and purpose

This rubric defines candidate-blind logical review of the manual validation,
debugging, and hardening needed to recreate represented coding work in a working
state. It is a development-label correction protocol, not an admitted estimator,
a probability model, an observation of historical labor, or a productivity
measure.

The reviewer receives immutable public-source identity, a coding-responsibility
title and category, scope, evidence IDs, an exact hidden-lineage digest, and an
overlap-group ID. Source coding hours, old manual-QA labels, seed and challenger
hours, totals, confidence, rationales, partition counts, and candidate formulas
must remain unavailable throughout review.

## Counterfactual worker and supplied context

Estimate the effort for one competent senior contractor who knows the relevant
implementation ecosystem, begins unfamiliar with the product domain, receives
the implementation-profile specification and design inputs, and does not use AI.
The worker is recreating the represented functional and quality state with
ordinary modern tools.

The packet describes a coding responsibility whose implementation is estimated
elsewhere. Review only the additional hands-on validation, diagnosis, correction,
and hardening needed to make that responsibility credibly work as represented.
Do not estimate a separate QA team or elapsed schedule.

## Included work

Include a bounded, responsibility-specific share of work such as:

- exercising important happy paths, boundary cases, and failure behavior;
- running and inspecting the relevant automated checks while diagnosing failures;
- using a representative harness, sample, CLI, UI, API, local service, or data
  fixture when that is the practical way to validate the behavior;
- tracing integration, serialization, persistence, concurrency, security,
  accessibility, build, delivery, or packaging behavior far enough to find and
  correct ordinary implementation defects;
- checking that tests meaningfully exercise the intended behavior rather than
  merely passing mechanically; and
- focused regression and hardening after the responsibility is integrated with
  adjacent represented work.

Libraries and infrastructure can require manual validation even without a visual
interface. Conversely, a large source surface does not automatically require a
large manual test campaign when representative automated checks and stable
conventions make validation straightforward.

## Excluded work

Do not include:

- specification comprehension, discovery, architecture, product design, or
  repository setup already represented elsewhere;
- implementation or automated-test authoring already represented by the source
  coding responsibility;
- documentation writing, self-review, pricing, management, handoffs, or waiting;
- historical rework, abandoned approaches, commit activity, contributor count,
  or actual elapsed time;
- exhaustive certification, formal penetration testing, a complete accessibility
  audit, production rollout, long-duration soak/load testing, or broad device and
  platform matrices unless the artifact materially represents that quality bar;
- remediation for missing professional practices; or
- repeated validation already assigned to another target.

The static analyzer's failure to execute target code is not itself an hours
multiplier. Estimate the counterfactual recreation work from the represented
behavior and quality boundary.

## Overlap and allocation

Review every target sharing an `overlapGroupId` together. Validation that covers
several responsibilities in one flow must be assigned once to the responsibility
that best owns it. Other targets receive only their distinct incremental
validation, or an explicit zero exclusion when the same work would otherwise be
duplicated.

Exact-scope grouping is an audit aid, not proof that different scopes never
overlap. Use evidence IDs and the pinned public source to detect shared harnesses,
generated or test-only signals, wrapper surfaces, and cross-scope integration
flows. Never multiply effort by evidence count, source partition count, file
volume, repository size, or the number of related targets.

## Range judgment

Reason low, expected, and high independently from the concrete validation work:

- **low**: a smooth recreation with representative checks working promptly;
- **expected**: the most credible bounded validation, debugging, and hardening
  path for the represented responsibility; and
- **high**: credible additional diagnosis or environment/interaction difficulty,
  without adding unrelated contingencies or an imagined professionalization gap.

Ranges are planning bounds, not formal probability intervals. Do not derive any
point from hidden source hours, a percentage, a repository total, or another model
output. Keep expected targets normally between 0.5 and 8 hours. A cohesive target
outside that band requires a concrete size exception explaining why further
decomposition would make the judgment less auditable.

## Explicit zero decisions

Use exactly `0/0/0` only when the source responsibility is wholly excluded,
false-positive, generated, duplicate, or already covered by another named target.
The rationale and size exception must identify that boundary. Zero does not mean
"easy," reuse, ordinary uncertainty, or a discount.

## Evidence and rationale

Each decision must:

- retain its source-target and hidden-lineage identities;
- cite the relevant evidence or public-source boundary without copying source
  excerpts;
- name the practical validation/debugging activities included;
- identify any overlap allocation or exclusion; and
- record the material uncertainty that separates low, expected, and high.

Review the targets before reconciling any category or repository total. A complete
decision set remains `teacher-estimate` weak supervision unless a genuinely
distinct review advances its maturity under the general calibration policy.
